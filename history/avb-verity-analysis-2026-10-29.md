## MECHANISM VERDICT

| Question | Verdict | Decisive evidence |
|---|---|---|
| **AVB (Android Verified Boot)** | **OFF** — not enabled, not signable, not supported by the kernel | `BOARD_AVB_ENABLE` is never defined anywhere in the build; `misc_info.txt` contains **no** `avb_*` keys; no `vbmeta*.img` exists; no `AVBf` footer in boot/recovery/vendor; kernel has **no** `CONFIG_DM_VERITY_AVB` / `CONFIG_ANDROID_VERIFIED_BOOT` symbol at all |
| **dm-verity (classic / vboot 1.0)** | **OFF at build time** — no hashtree, no verity key, no signing | `PRODUCT_SUPPORTS_VERITY` never set → `misc_info.txt` has no `verity=` key; the only `verify` flag lives in the **recovery-only** fstab and has no metadata to act on |
| **system-as-root (legacy `BOARD_BUILD_SYSTEM_ROOT_IMAGE`)** | **NO** (flag unset) — but the build emits a **ramdisk-init (first-stage) boot image** | `BOARD_BUILD_SYSTEM_ROOT_IMAGE` unset; `boot.img` ramdisk contains a real 1,372,192-byte first-stage `/init` binary |
| **SELinux** | **Permissive at boot** | `androidboot.selinux=permissive` is in `BoardConfig.mk:47` **and** confirmed byte-for-byte inside the built `boot.img` |
| **Encryption** | **OFF in normal boot**, inconsistently requested in recovery fstab | `fstab.qcom:37` has no `forceencrypt`/`fileencryption`; `fstab.recovery.qcom:37` has `forceencrypt=footer`; kernel `CONFIG_FS_ENCRYPTION` is not set |

**Bottom line for the colleague:** this build has **no integrity verification layer whatsoever** — no AVB, no verity, no vbmeta. Nothing in the boot chain can reject a modified `boot`/`system`/`vendor` image, and there is no dm-verity corruption message to chase. A boot failure here **cannot** be a verity/AVB rejection; look elsewhere. The strongest structural suspect found is that the **boot ramdisk contains no fstab at all** while `/vendor/etc/fstab.qcom` marks `/system` as `recoveryonly` and has **no `/vendor` entry** (see §2.3).

### Two independent confirmations of "no AVB"

1. **No `AVBf` magic** in the footer region of any image.

## 7. Summary for diagnosis

1. **No verification mechanism is active.** Not AVB, not classic verity. Nothing will reject a tampered image; there is no `vbmeta` partition content to mismatch and no verity hashtree to corrupt.
2. **The kernel cannot do AVB even if asked** (`CONFIG_DM_VERITY_AVB` does not exist in this 3.18 tree).
3. **Do not chase verity/AVB errors.** A boot failure on this build must be diagnosed from other angles.
4. **The most concrete structural anomaly found:** boot ramdisk has **no fstab**; the shipped `/vendor/etc/fstab.qcom` has **no `/vendor` line** and marks `/system` `recoveryonly`. **UNVERIFIED** whether this is the actual failure (needs a boot log / `dmesg` from the device).
5. **SELinux is permissive** in the built `boot.img` — SELinux denials will be logged but will not block boot. If the colleague is reading `avc: denied` messages, they are almost certainly *not* the cause.
6. **Inconsistency to be aware of:** normal-boot fstab requests **no** encryption on `/data`, while the recovery fstab requests `forceencrypt=footer`; the kernel has `CONFIG_FS_ENCRYPTION` unset, so `forceencrypt` in recovery cannot succeed as configured.

### Explicitly UNVERIFIED

- Runtime behaviour of the `verify` flag in `fstab.recovery.qcom:36` with no verity metadata present.
- Whether/how `/system` and `/vendor` actually get mounted at normal boot (no fstab in ramdisk; needs on-device boot log).
- Why `system.img` is absent from `out/target/product/j8y18lte/` (build incomplete/cleaned — not determinable from artefacts alone).
